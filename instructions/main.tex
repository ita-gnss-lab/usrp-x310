\section{Hardware used}

The setup considered here is:

\begin{itemize}[leftmargin=*]
    \item Ettus USRP X310;
    \item one TwinRX Rev.~C receive daughterboard;
    \item TwinRX provides two receive front-ends/channels: RX0 and RX1;
    \item the second X310 daughterboard slot is empty;
    \item Ubuntu host computer connected to X310 port~0 through Ethernet;
    \item external 10~MHz frequency reference connected to \texttt{REF IN};
    \item no external PPS is connected;
    \item Python 3.12 with UHD's Python bindings (\texttt{python3-uhd}) and the \texttt{sigmf} package, managed with \texttt{uv}.
\end{itemize}

The TwinRX is receive-only. Therefore, the current setup has two usable receive channels and no usable RF transmit chain.

\section{Useful Linux network checks}

Check the interface state:

\begin{lstlisting}[language=bash]
ip -br addr show enp109s0
\end{lstlisting}

Replace \texttt{enp109s0} with the actual NIC (Network Interface Controller/Card) name if it is different in your machine. A correct configuration should show approximately:

\begin{lstlisting}
enp109s0   UP   192.168.10.1/24
\end{lstlisting}

Check the physical Ethernet carrier:

\begin{lstlisting}[language=bash]
cat /sys/class/net/enp109s0/carrier
\end{lstlisting}

Interpretation:

\begin{itemize}[leftmargin=*]
    \item \texttt{1}: physical Ethernet link detected;
    \item \texttt{0}: no physical Ethernet carrier.
\end{itemize}

The same check can be performed with:

\begin{lstlisting}[language=bash]
ethtool enp109s0 | grep "Link detected"
\end{lstlisting}

For a working 1~GbE link, \texttt{ethtool enp109s0} should normally report:

\begin{lstlisting}
Speed: 1000Mb/s
Duplex: Full
Link detected: yes
\end{lstlisting}

Check routing to the radio:

\begin{lstlisting}[language=bash]
ip route get 192.168.10.2
\end{lstlisting}

The route should use \texttt{enp109s0}, not Wi-Fi. A correct result is approximately:

\begin{lstlisting}
192.168.10.2 dev enp109s0 src 192.168.10.1
\end{lstlisting}

Test connectivity:

\begin{lstlisting}[language=bash]
ping -c 4 192.168.10.2
\end{lstlisting}

\section{Python environment setup}

Recording is done with a small set of Python scripts (\texttt{x310usrp\_record.py}, \texttt{check\_levels.py}, \texttt{report\_summary.py}) in the project repository, managed with \texttt{uv}. UHD's Python bindings come from the \texttt{python3-uhd} apt package and only work with the system Python~3.12, so the \texttt{uv} virtual environment must be created with system site-packages enabled rather than a fully isolated one:

\begin{lstlisting}[language=bash]
cd usrp-x310
rm -rf .venv
uv venv --python /usr/bin/python3 --system-site-packages
uv sync
\end{lstlisting}

\texttt{uv sync} installs the project's remaining dependencies declared in \texttt{pyproject.toml}: \texttt{numpy} (version-pinned to stay ABI-compatible with the system numpy that \texttt{python3-uhd} was built against) and \texttt{sigmf}, the official SigMF-project library used to build and validate the recording files.

\section{Recording I/Q samples with \texttt{x310usrp\_record.py}}

\texttt{x310usrp\_record.py} streams both TwinRX channels straight to disk and bundles the result into a single SigMF Archive. Typical usage:

\begin{lstlisting}[language=bash]
uv run x310usrp_record.py --duration 5                        # L1 + L5, 5 s
uv run x310usrp_record.py --freq 1575.42e6 --channels 0       # L1 only
uv run x310usrp_record.py --iq-rate 4e6 20e6 --gain 25 30 --name test1  # per channel
uv run x310usrp_record.py --help                               # all options, with defaults
\end{lstlisting}

The defaults reproduce the dual-frequency GNSS setup used in this lab: GPS L1 (1575.42~MHz) on RX0 at 4~MS/s and GPS L5 (1176.45~MHz) on RX1 at 20~MS/s, with the external 10~MHz clock reference and 25~dB of RX gain on both channels (see Section~\ref{sec:gain}). \texttt{--freq}, \texttt{--gain} and \texttt{--iq-rate} each take either one value (applied to every channel) or one value per channel; when \texttt{--iq-rate} is omitted, each channel's rate is chosen from the band it is tuned to (4~MS/s for L1, whose C/A main lobe is about 2~MHz wide, and 20~MS/s for L5, whose 10.23~Mchip/s main lobe is about 20~MHz wide).

Because the two channels run at different sample rates, each channel is received through its own UHD streamer, in its own thread, and written to its own \texttt{.sigmf-data} file. Both streamers are started by the same timed stream command, so the two recordings still begin at the same instant on the USRP's clock. Every per-channel quantity -- sample rate, gain, frequency, written and lost samples -- is stored in that channel's own \texttt{.sigmf-meta} and reported per channel.

\subsection{SigMF Archive output}

Each run produces a single file, \texttt{recordings/<name>.sigmf}, following the SigMF specification's Archive~$\rightarrow$~Collection~$\rightarrow$~Recording structure: the \texttt{.sigmf} file is a plain tar archive containing one \texttt{.sigmf-collection} JSON file (linking the two channels' recordings by name and SHA-512 hash) and, for each channel, one \texttt{.sigmf-meta} (JSON metadata: that channel's sample rate, frequency, gain, antenna, motherboard/daughterboard, start time, lost/written sample counts) and one \texttt{.sigmf-data} file (interleaved \texttt{int8} I/Q, SigMF datatype \texttt{ci8}: 1 byte for I and 1 byte for Q, 2 bytes per complex sample). Listing one archive's contents:

\begin{lstlisting}[language=bash]
tar -tvf recordings/x310_20261009T160000Z.sigmf
\end{lstlisting}

\begin{lstlisting}
x310_20261009T160000Z/x310_20261009T160000Z.sigmf-collection
x310_20261009T160000Z/x310_20261009T160000Z_ch0.sigmf-meta
x310_20261009T160000Z/x310_20261009T160000Z_ch1.sigmf-meta
x310_20261009T160000Z/x310_20261009T160000Z_ch0.sigmf-data
x310_20261009T160000Z/x310_20261009T160000Z_ch1.sigmf-data
\end{lstlisting}

The X310 only sends 16-bit samples over the wire (OTW format \texttt{sc16}): asking UHD for \texttt{sc8} is accepted without any error, but the X310 keeps sending \texttt{sc16} and UHD then misreads every 16-bit value as an 8-bit I/Q pair, which is what corrupted the recordings of 19--20/10/2026. \texttt{x310usrp\_record.py} therefore refuses any OTW or CPU format other than \texttt{sc16} at startup, receives \texttt{sc16}, and writes it either unchanged or converted to 8 bits. Without \texttt{--int8-div}, the samples are written exactly as received (SigMF \texttt{ci16\_le}, 4~bytes per sample). With \texttt{--int8-div}, the script converts to 8 bits itself before writing (SigMF \texttt{ci8}, 2~bytes per sample): each value is divided by the per-channel divisor (one value, or one per channel), rounded, and saturated to $\pm$127. The scheduled service passes \texttt{--int8-div 1 3} (1 for L1, 3 for L5), which puts the noise standard deviation at about 30 of 127 at 25~dB gain, rounded, and saturated to $\pm$127. The divisor and the number of saturated values are stored in each channel's \texttt{.sigmf-meta} (\texttt{x310:int8\_div}, \texttt{x310:clipped\_values}), and a warning is logged if more than 0.01\,\% of a channel's values saturate. The link still carries 4~bytes per sample, so the default 4 + 20~MS/s costs 4~bytes~$\times$~24~MS/s = 96~MB/s, close to the roughly 100~MB/s a 1~GbE link can carry; only the files on disk are halved (and only with \texttt{--int8-div}). If the host falls behind anyway (an overflow), the lost samples are replaced by zeros, so a sample's position in the file always matches its time and the two channels stay aligned; each gap is logged on the console and recorded in that channel's \texttt{.sigmf-meta} as an annotation covering the zero-filled samples, and in its \texttt{x310:lost\_samples} total. Recordings made before 19/10/2026 skipped lost samples instead of zero-filling them, and over-counted \texttt{x310:lost\_samples}. X310 rates are 200~MHz divided by an integer (4 and 20~MS/s are exact: 200/50 and 200/10), so other requested rates may be coerced; the script prints the actual value used per channel.

At these rates a 300~s recording takes about 2.4~GB for L1 and 12~GB for L5, i.e.\ about 14.4~GB per recording and 29~GB per day.

\subsection{Loading the recorded samples in Python}

Each channel's complex I/Q samples can be read directly out of the archive without extracting it to disk first:

\begin{lstlisting}[language=Python]
import tarfile
import numpy as np

with tarfile.open("recordings/x310_20261009T160000Z.sigmf") as tar:
    member = next(m for m in tar.getmembers() if m.name.endswith("_ch0.sigmf-data"))
    raw = tar.extractfile(member).read()

L1 = np.frombuffer(raw, dtype=np.int8).astype(np.float32).view(np.complex64)
\end{lstlisting}

Replace \texttt{\_ch0} with \texttt{\_ch1} for the GPS~L5 channel. The two channels have different sample rates (and hence different numbers of samples for the same duration), so always read each channel's rate from its own \texttt{.sigmf-meta} (\texttt{core:sample\_rate}) rather than assuming a common one.

\section{Checking signal levels and choosing \texttt{--gain}}
\label{sec:gain}

TwinRX's RX gain is a fixed, manually-set Programmable Gain Amplifier (PGA) stage, not an AGC loop (UHD's generic \texttt{set\_rx\_agc()} call raises \texttt{NotImplementedError} on TwinRX) -- so the right gain has to be chosen once and does not adjust itself during a recording.

Because GNSS signals sit 15--20~dB below the thermal noise floor, there is no ``signal'' to look for when picking a gain: the real goal is placing the composite \emph{noise floor} correctly within the ADC's dynamic range -- high enough that quantization noise does not matter, low enough that strong interferers do not clip the rails. \texttt{check\_levels.py} reports exactly this, directly from an archive's raw samples:

\begin{lstlisting}[language=bash]
uv run x310usrp_record.py --duration 10 --gain 20 25   # one gain per channel
uv run check_levels.py recordings/x310_<timestamp>.sigmf
\end{lstlisting}

It prints each channel's I/Q standard deviation against a target band (1/16 to 1/3 of full-scale: 128 for the current \texttt{int8} samples, i.e.\ 8 to 42; 32768 for older \texttt{int16} recordings) and the percentage of clipped samples, with a one-line verdict (raise/lower \texttt{--gain}, or OK). With a 20~dB external active LNA already in this lab's RF chain ahead of the USRP, the TwinRX gain is set to \textbf{25~dB} on both channels. Since the L5 channel's 20~MS/s bandwidth lets in about 7~dB more noise power than the L1 channel's 4~MS/s, the two channels sit at different levels for the same gain, so \texttt{check\_levels.py} should be read per channel. This matters more with 8-bit samples, which have only $\pm$127 of headroom: if a channel saturates, raise its \texttt{--int8-div} (or lower its gain); if one channel falls outside the target band, give it its own value via \texttt{--gain <ch0> <ch1>}. Re-run the check if the antenna, cable, or LNA changes.

\section{Automating recordings with systemd}
\label{sec:record-service}

Scheduled, unattended recording is driven by a timer/service pair in \texttt{systemd/}, enforcing (independently of the timer's own schedule, so a manual trigger or a missed/caught-up run can never violate them):

\begin{itemize}[leftmargin=*]
    \item recording only inside the \texttt{[16:00, 18:00)} local-time window;
    \item at most two recordings per calendar day;
    \item the second recording starting at least 30~min after the first;
    \item sensing the USRP via \texttt{uhd\_find\_devices} before attempting to record, retrying silently every 15~min if it is not reachable;
    \item recording to a local staging directory (\texttt{staging/}, skipped if it has less than 35~GB free) and only then moving the finished archive to the NAS (\texttt{recordings/} links to it). Writing directly to the NAS over SMB stalls the receive loop for about 100~ms at a time, longer than the roughly 70~ms the L5 channel's receive buffer lasts at 40~MB/s, which drops samples. The archive is moved with \texttt{rsync -rt --remove-source-files}, which writes it under a hidden temporary name and renames it only once complete (so the NAS never shows a truncated \texttt{.sigmf}), and deletes the local copy only after a successful transfer; if the NAS is unreachable, the archive stays in \texttt{staging/} and is moved on the next run.
\end{itemize}

Manual recordings should likewise use a local directory, e.g.\ \texttt{uv run x310usrp\_record.py --staging-dir staging}, and be moved to the NAS afterwards.

\texttt{x310-record.timer} fires every 15~min between 16:00 and 18:00; \texttt{x310-record.sh} (invoked by \texttt{x310-record.service}) is what actually evaluates all of the conditions above and, if they pass, runs \texttt{x310usrp\_record.py}. Install and enable it with:

\begin{lstlisting}[language=bash]
sudo ln -s $PWD/systemd/x310-record.service /etc/systemd/system/
sudo ln -s $PWD/systemd/x310-record.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now x310-record.timer
\end{lstlisting}

Using symlinks rather than copying the unit files means editing them in the repository takes effect after a \texttt{daemon-reload}, with no separate install step. Check what is scheduled, and inspect a run's output, with:

\begin{lstlisting}[language=bash]
systemctl list-timers x310-record.timer
journalctl -u x310-record.service
\end{lstlisting}

\section{Fortnightly WhatsApp report}
\label{sec:report-service}

Every 15~days, a short text summary and a compiled PDF of this very report are sent over WhatsApp to the lab head, via a self-hosted \href{https://github.com/rmyndharis/OpenWA}{OpenWA} gateway. OpenWA automates the unofficial WhatsApp Web client (not Meta's official API), so its own documentation notes a real, non-zero account-ban risk; using a dedicated number rather than a personal one is recommended.

\subsection{One-time OpenWA setup}

\begin{lstlisting}[language=bash]
git clone https://github.com/rmyndharis/OpenWA && cd OpenWA
docker compose -f docker-compose.dev.yml up -d
docker exec openwa-api cat /app/data/.api-key   # save as OPENWA_API_KEY
\end{lstlisting}

Create a session (the \texttt{"name"} given here is only a label; OpenWA assigns its own UUID, returned as \texttt{"id"}, which is what every later call -- including \texttt{OPENWA\_SESSION} below -- must use):

\begin{lstlisting}[language=bash]
curl -X POST http://localhost:2785/api/sessions \
     -H "X-API-Key: $OPENWA_API_KEY" -H "Content-Type: application/json" \
     -d '{"name": "x310-notifier"}'
\end{lstlisting}

Start it and fetch its QR code, then scan the QR with the WhatsApp account that should send the reports (WhatsApp app~$\rightarrow$~Linked Devices~$\rightarrow$~Link a Device):

\begin{lstlisting}[language=bash]
curl -X POST http://localhost:2785/api/sessions/<uuid>/start -H "X-API-Key: $OPENWA_API_KEY"
curl http://localhost:2785/api/sessions/<uuid>/qr -H "X-API-Key: $OPENWA_API_KEY"
\end{lstlisting}

Finally, store the three secrets the report service needs in a \texttt{.env} file at the repository root (already excluded from version control):

\begin{lstlisting}
OPENWA_API_KEY=<api key from above>
OPENWA_SESSION=<session uuid from above>
REPORT_WHATSAPP_TO=<recipient phone number, e.g. +55...>
\end{lstlisting}

\subsection{\texttt{report\_summary.py}}

On each run, \texttt{report\_summary.py} scans \texttt{recordings/} for every \texttt{.sigmf} archive newer than the last report (tracked in a state file, defaulting to 15~days back on first run); for those, it

\begin{enumerate}[leftmargin=*]
    \item sends a short WhatsApp text digest -- recording counts, data volume, lost samples, and which days (if any) had no recording;
    \item appends one subsection per day (holding one sub-subsection per recording that day, each a metadata table) and refreshes the recording-calendar table in \texttt{report/main.tex};
    \item recompiles \texttt{report/main.tex} and sends the resulting PDF as a WhatsApp document.
\end{enumerate}

Run manually, loading the secrets from \texttt{.env}:

\begin{lstlisting}[language=bash]
uv run --env-file .env report_summary.py
\end{lstlisting}

\subsection{Automating the report}

Analogous to the recording service, \texttt{x310-report.timer} fires \texttt{x310-report.service} on a \emph{relative} schedule -- exactly 15~days after the previous run, rather than approximating with calendar-day arithmetic:

\begin{lstlisting}[language=bash]
sudo ln -s $PWD/systemd/x310-report.service /etc/systemd/system/
sudo ln -s $PWD/systemd/x310-report.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now x310-report.timer
\end{lstlisting}

\section{Clock source, time source, and LO source}

These three settings have different purposes. They are set directly as command-line flags to \texttt{x310usrp\_record.py} (see also Section~\ref{sec:record-service}'s underlying \texttt{uv run x310usrp\_record.py} invocation).

\subsection{Clock source}

The clock source provides the precision frequency reference used by the radio clocking and synthesizers.

With an external 10~MHz reference connected to \texttt{REF IN}, use:

\begin{lstlisting}[language=bash]
--clock-source external
\end{lstlisting}

The 10~MHz reference does not enter through an RF receive connector.

\subsection{Time source}

The time source establishes the timing reference for the radio time counter, typically through a 1~PPS signal.

Because no external PPS is connected in the present setup, use:

\begin{lstlisting}[language=bash]
--time-source internal
\end{lstlisting}

If a 1~PPS signal were connected to the X310 PPS input, \texttt{--time-source external} could be used; \texttt{x310usrp\_record.py} then also waits for a PPS edge to actually be detected (by checking that \texttt{get\_time\_last\_pps()} advances between two reads) before recording, since UHD has no boolean ``PPS locked'' sensor the way it does for the reference clock and the LOs.

\subsection{LO source}

The LO is the RF local oscillator used by the mixer to translate the received RF signal to IF/baseband. \texttt{x310usrp\_record.py} always uses each channel's internal LO synthesizer, referenced to the external 10~MHz signal selected above:

\begin{center}
External 10~MHz $\rightarrow$ REF IN $\rightarrow$ internal PLL/synthesizer $\rightarrow$ RF LO $\rightarrow$ mixer
\end{center}

An external LO would instead mean supplying the actual RF LO signal from an external RF generator -- not the same thing as the 10~MHz reference, which is the wrong frequency for the RF mixing stage.

\section{Two-channel TwinRX tuning}

TwinRX has two receive channels. Their LO configuration determines whether they can be tuned independently.

\subsection{Same frequency with phase coherence}

For two channels receiving the same RF frequency with phase coherence, LO sharing can be used: one channel generates the LO and the other uses it as a companion. This is appropriate when both channels observe the same RF band and relative phase is important. \texttt{x310usrp\_record.py} does not use this mode.

\subsection{Different frequencies}

For independent center frequencies, both channels must use independent internal LOs -- TwinRX phase synchronization must not be enabled. This is exactly the case here:

\begin{itemize}[leftmargin=*]
    \item Channel 0: GPS L1 = 1575.42~MHz;
    \item Channel 1: GPS L5 = 1176.45~MHz.
\end{itemize}

Because L1 and L5 are separated by about 399~MHz, they cannot be obtained from one shared analog LO using only a digital frequency offset; they require independent analog LO tuning, which is what each channel's own \texttt{set\_rx\_freq} call in \texttt{x310usrp\_record.py} sets up.

\section{Verifying lock status}

Before streaming, \texttt{x310usrp\_record.py} waits for the reference clock and both channels' LOs to report locked, raising a clear error after a timeout rather than silently recording against an unlocked radio. The same sensors can also be queried directly, independent of the Python script, with:

\begin{lstlisting}[language=bash]
uhd_usrp_probe --args="addr=192.168.10.2" --tree | grep lo_locked
\end{lstlisting}

For this X310, the paths are (the exact path may vary with UHD version):

\begin{lstlisting}
/blocks/0/Radio#0/dboard/rx_frontends/0/sensors/lo_locked
/blocks/0/Radio#0/dboard/rx_frontends/1/sensors/lo_locked
\end{lstlisting}

Check a given channel directly:

\begin{lstlisting}[language=bash]
uhd_usrp_probe \
  --args="addr=192.168.10.2" \
  --sensor="/blocks/0/Radio#0/dboard/rx_frontends/0/sensors/lo_locked"
\end{lstlisting}

For a healthy configuration, this returns \texttt{true} for both channels -- matching what \texttt{x310usrp\_record.py} itself reports as \texttt{ch0 lo\_locked: locked} / \texttt{ch1 lo\_locked: locked} on its own console output during a normal run.

\section{RFNoC block-factory warnings}

When probing or using the radio, warnings such as the following may appear:

\begin{lstlisting}
[WARNING] [RFNOC::BLOCK_FACTORY]
Could not find block with Noc-ID ...
\end{lstlisting}

These appear routinely during normal \texttt{x310usrp\_record.py} runs on this FPGA image and have not prevented successful communication with the X310, streaming, or access to the TwinRX lock sensors. The radio still enumerates normally, and standard blocks such as the DDCs, DUCs, radios, replay block, and TwinRX daughterboard remain visible.

\section{Recommended final configuration}

For the current L1/L5 dual-frequency GNSS recording setup:

\begin{lstlisting}
Host Ethernet IP:   192.168.10.1/24
X310 IP:            192.168.10.2
Ethernet:           1 GbE, port 0
MTU:                1500

Clock Source:       external
Time Source:        internal
LO Source RX0:      internal
LO Source RX1:      internal

TwinRX RX0:         GPS L1 = 1575.42 MHz
TwinRX RX1:         GPS L5 = 1176.45 MHz
Sample rate RX0:    4 MS/s  (L1)
Sample rate RX1:    20 MS/s (L5)
Gain RX0/RX1:       25 dB / 25 dB (Section~\ref{sec:gain})
Sample type:        sc16 over the wire, ci8 on disk (int8 I + int8 Q = 2 bytes)
int8 divisor:       1 (L1) / 3 (L5)
Recording length:   300 s (5 min), up to twice per day, 16:00-18:00 local time
\end{lstlisting}

Equivalently, as the command this whole configuration reduces to when run manually:

\begin{lstlisting}[language=bash]
uv run x310usrp_record.py
\end{lstlisting}

since every value above is already \texttt{x310usrp\_record.py}'s own default. This configuration gives independent L1/L5 tuning while keeping both LO synthesizers referenced to the same precision external 10~MHz source, with unattended scheduling and reporting handled by the services in Sections~\ref{sec:record-service} and~\ref{sec:report-service}.
